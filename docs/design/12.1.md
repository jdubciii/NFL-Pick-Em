# Phase 12.1 Design Note: Outbox Pattern & Background Job Scheduler

## 1. Overview & Objectives
Phase 12.1 establishes an asynchronous, resilient background processing architecture for NFL Pick'em. The primary goal is to decouple critical transactional mutations (e.g. pick submissions, pool membership updates, weekly wrap-ups) from downstream side-effects (e.g. notification dispatch, audit streaming, statistical rollups) via an Outbox Pattern.

---

## 2. Planned Architecture & Components

### 2.1 Files to Add
The following files are planned for addition in Phase 12.1 (strictly keeping application code out of `src/` during Phase 12.0 / R-12.2-AF):
- `src/services/outbox.ts`: Transactional outbox event publisher and batch processor.
- `src/services/lockResolver.ts`: Extracted, centralized game/pool lock resolution engine.
- `src/jobs/scheduler.ts`: Internal job scheduler loop managing interval timers for background tasks.
- `src/jobs/handlers/wrapupHandler.ts`: Asynchronous executor for weekly wrap-up jobs.
- `src/jobs/handlers/notificationHandler.ts`: Asynchronous executor for email/push/webhook notifications.
- `tests/outbox.test.ts`: Integration tests for outbox transactional persistence, processing, and retry lifecycles.
- `tests/lockResolver.test.ts`: Unit and characterization tests for lock-offset resolution rules.
- `tests/scheduler.test.ts`: Concurrency and timer tests for the internal scheduler.

## 3. Lock-Resolver Extraction Plan

### Current State
Game locking logic and lock offset evaluation (`lock_offset` from `pool.settings`) are currently computed inline within `src/server.ts`, `src/routes/games.ts`, `src/routes/picks.ts`, and `src/services/weeklyWrapUp.ts`.

### Target Extraction
Extract all lock calculation and verification into a standalone, pure, deterministic module: `src/services/lockResolver.ts`.

#### Interface Specification
```typescript
export interface LockContext {
  kickoffTime: Date;
  lockOffsetMinutes: number;
  now?: Date;
}

export interface LockStatus {
  isLocked: boolean;
  effectiveLockTime: Date;
  minutesRemaining: number;
}

export function computeGameLockStatus(context: LockContext): LockStatus;
export function isGameLocked(kickoffTime: Date, lockOffsetMinutes: number, now?: Date): boolean;
export function assertGameUnlocked(kickoffTime: Date, lockOffsetMinutes: number, now?: Date): void;
```

#### Migration Strategy
1. Implement `src/services/lockResolver.ts` with exhaustive unit tests across edge cases (negative offsets, 0 offsets, post-kickoff, timezone variations).
2. Refactor route handlers (`/api/picks`, `/api/games`) to consume `assertGameUnlocked` and `computeGameLockStatus`.
3. Verify zero behavioral regression using existing integration suites.

## 4. Scheduler Trigger Mechanism

### Constraints
- **No external cron library** (e.g., `node-cron`, `cron`, `agenda`) to keep the runtime lightweight, dependency-safe, and deterministic.
- Fully controlled via environment flags: `INTERNAL_JOBS_ENABLED=true`.

### Implementation Pattern
- **Scheduler Loop**: Native `setInterval` / recursive `setTimeout` loop initialized conditionally upon server startup:
  ```typescript
  if (process.env.INTERNAL_JOBS_ENABLED === 'true') {
    startSchedulerLoop();
  }
  ```
- **Manual Trigger Endpoint**:
  - Secure commissioner/admin endpoint `POST /api/admin/jobs/run` guarded by `requireAuth` and `requireAdmin` for on-demand execution and test harness invocations.
- **Fail-Safe Graceful Shutdown**:
  - Register `SIGTERM` / `SIGINT` hooks to clear active intervals and await completion of in-flight outbox batches.

## 5. Outbox & Inbox Event Lifecycle

```
[ HTTP Route Handler ]
       │ (Prisma Transaction)
       ├─── Writes Domain Entity (e.g. Pick, WrapUp)
       └─── Writes OutboxEvent (topic, payload, status: PENDING)
       │
[ Database / PostgreSQL ]
       │
[ Polling Job / Scheduler ] (INTERNAL_JOBS_ENABLED=true)
       │
       ├─── SELECT ... FROM outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED
       ├─── Execute Handlers
       └─── UPDATE outbox_events SET status = 'PROCESSED', processed_at = NOW()
```

## 6. Open Questions & Architectural Considerations
1. **Advisory Locking / Multi-Instance Concurrency**:
   - If multiple server instances run simultaneously, should we use PostgreSQL advisory locks (`pg_try_advisory_lock`) or `FOR UPDATE SKIP LOCKED` for outbox polling?
2. **Dead Letter Queue (DLQ) & Retry Policy**:
   - What max-retry count (e.g., 3 or 5) and exponential backoff interval should be enforced before marking an event `FAILED`?
3. **Event Retention / Cleanup**:
   - Should processed outbox events be retained permanently for audit trails or purged after a configurable TTL (e.g., 30 days)?
